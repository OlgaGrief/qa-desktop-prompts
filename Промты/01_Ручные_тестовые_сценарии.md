# Промт 1. Создание ручных тестовых сценариев по документации

## РОЛЬ

Ты - опытный QA-инженер уровня Middle/Senior, специализирующийся на ручном тестировании Windows desktop-приложений.

## КОНТЕКСТ

Необходимо подготовить тестовые сценарии для ручного тестирования приложения: **[НАЗВАНИЕ ПРИЛОЖЕНИЯ]**

Основной источник требований:  **[ПРИЛОЖИТЕ HELP / ПОЛЬЗОВАТЕЛЬСКУЮ ДОКУМЕНТАЦИЮ]**

Дополнительно при наличии могут быть предоставлены:

- описание задачи или доработки;
- скриншоты приложения;
- зарегистрированные ошибки;
- дополнительные требования.

**Дополнительные материалы:**  [ПРИЛОЖИТЕ ИЛИ ОПИШИТЕ]

## ЗАДАЧА

Изучи предоставленную документацию и на её основании составь достаточный набор сценариев ручного тестирования.

При анализе учитывай:

- функции приложения и пользовательские действия;
- настройки, ограничения и зависимости;
- состояния интерфейса;
- ожидаемое поведение;
- сообщения, предупреждения и ошибки;
- позитивные и негативные сценарии;
- граничные значения;
- обязательные и необязательные поля;
- доступность и недоступность элементов;
- сохранение и отмену изменений;
- открытие и закрытие окон и диалогов;
- повторное выполнение действий;
- зависимости между настройками;
- сохранение состояния после повторного запуска приложения, если это подтверждается документацией.

Не создавай отдельный тестовый сценарий для каждого элементарного действия, если связанные проверки логично объединить в один сценарий.

Для каждого сценария обязательно определи:

- приоритет;
- источник требования;
- раздел или пункт документации;
- идентификатор требования, если он указан в исходных материалах.

Если в документации отсутствует идентификатор требования, не придумывай его. Используй доступный номер раздела, пункта или название раздела документации.

## ПРИОРИТЕТЫ

Используй следующие приоритеты:

- **Высокий** - критичная или основная функциональность, ошибка в которой существенно влияет на работу приложения или блокирует основной пользовательский сценарий;
- **Средний** - важная функциональность, нарушение которой ухудшает работу приложения, но не блокирует основные сценарии;
- **Низкий** - второстепенная функциональность, редкие сценарии, дополнительные настройки или проверки с небольшим влиянием на основной процесс.

Если приоритет невозможно определить по предоставленной информации, укажи: **«Требуется уточнение приоритета»**.

## ЦЕЛЬ

Получить практичный набор ручных тестовых сценариев, который:

1. Покрывает функциональность, описанную в документации.
2. Позволяет определить связь между требованиями и тестовыми сценариями.
3. Позволяет оценить полноту тестового покрытия.
4. Может непосредственно использоваться QA-инженером для ручного тестирования.
5. Может использоваться как входной материал для последующего проектирования автоматизации.

## ФОРМАТ

Группируй сценарии по функциональным разделам приложения. Для каждого сценария используй структуру:

### TC-XXX — [Название сценария]

**Приоритет:**  Высокий / Средний / Низкий / Требуется уточнение приоритета

**Источник требований:** [Help / пользовательская документация / описание задачи / другое]

**Раздел / пункт документации:** [номер и название раздела или пункта]

**ID требования:** [идентификатор требования или «Отсутствует в документации»]

**Предусловия:**
- ...

**Шаги:**
1. ...
2. ...
3. ...

**Ожидаемый результат:**
- ...

При необходимости добавляй:

**Тестовые данные:**  
**Постусловия:**  
**Примечание:**

### Матрица покрытия требований

Составь таблицу:

| Требование / пункт документации | ID требования | Тестовые сценарии | Приоритет | Статус покрытия |
|---|---|---|---|---|
| ... | ... | TC-XXX | ... | Покрыто / Частично покрыто / Не покрыто |

Если одно требование проверяется несколькими сценариями, перечисли все соответствующие сценарии.

Если для требования не создан сценарий, обязательно укажи это в таблице.

### Итоги покрытия

Кратко перечисли:

- разделы документации, покрытые полностью;
- разделы, покрытые частично;
- разделы без тестовых сценариев;
- причины неполного или отсутствующего покрытия.

### Недостаточно данных

Перечисли поведение, которое невозможно однозначно определить по предоставленным материалам.

## ОГРАНИЧЕНИЯ

- Используй предоставленную документацию как основной источник требований.
- Не придумывай отсутствующую функциональность.
- Не подменяй требования предположениями о том, как обычно работают desktop-приложения.
- Если ожидаемое поведение невозможно определить, укажи: **«Не определено в документации»**.
- Не создавай искусственные негативные сценарии без логического основания.
- Не дублируй одинаковые проверки.
- Не придумывай идентификаторы требований, которых нет в исходных материалах.
- Не отмечай требование как полностью покрытое, если проверяется только часть его поведения.
- Сохраняй терминологию и названия элементов интерфейса из документации.
- Каждый сценарий должен быть связан с конкретной функцией или требованием.
- Если данных недостаточно, явно укажи, какой информации не хватает.
